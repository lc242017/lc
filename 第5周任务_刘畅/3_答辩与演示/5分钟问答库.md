# 5 分钟答辩问答库

> 项目：云购生活新零售——企业级数据仓库与经营分析可视化系统
> 覆盖手册要求的四类高频问题：建模依据 / 指标口径 / AI 边界 / 部署原理
> 用法：每题"要点 + 展开"，先答结论再给理由，控制 30~45 秒/题。

---

## 一、建模依据类

### Q1：为什么采用四层数仓（ODS/DWD/DWS/ADS）而不是直接查询？
**要点**：分层解耦、口径统一、性能与可复用。
**展开**：ODS 保留原始可追溯；DWD 做清洗和维度建模，保证数据质量；DWS 做轻度汇总支撑多维分析；ADS 面向应用预聚合。分层后每一层职责单一，口径在层间逐级固化，出问题可逐层定位，且 ADS 预聚合让在线查询提速 71%。

### Q2：为什么用星型模型？事实表和维度表怎么判定？
**要点**：查询路径短、易理解；事实表存度量，维度表存描述属性。
**展开**：星型模型适合经营分析，Join 层级少。事实表是"业务过程"——订单、用户行为；维度表是"观察角度"——日期、用户、商品、门店、渠道。总线矩阵明确了每个业务过程涉及哪些维度。

### Q3：为什么 GMV 预测用线性回归，不用更复杂的模型？
**要点**：数据规模与可解释性权衡。
**展开**：教学数据量级（15,000 单、12 个月）下，线性回归可解释性强、训练快、不易过拟合；先做趋势分解再回归，已经能捕捉主要趋势。复杂模型（如季节分解、XGBoost）在依赖就绪后可升级，但需更多数据支撑，否则方差大。

### Q4：为什么要单独建 `dwd_order_item` 明细事实表？
**要点**：手册差异 D2，避免 GMV 翻倍。
**展开**：手册让用 `dwd_order.product_id` 关联商品维度，但订单表是"一单一品"粒度、没有商品明细字段；强行加字段会导致订单行膨胀、GMV 翻倍。所以新增明细事实表，品类分析走明细粒度，订单金额走订单粒度，各归其位。

## 二、指标口径类

### Q5：GMV 是怎么定义的？含不含退款？
**要点**：实付口径，`status='paid'`，剔除退款。
**展开**：`GMV = sum(pay_amount) where status='paid'`，即已支付且未退款的实付金额之和，不含运费和优惠券补贴。退款单在 DWD 已打标，DWS/ADS 不再二次过滤。这套口径写在指标定义文档里，是全系统唯一事实源。

### Q6：客单价能不能直接 `avg(pay_amount)`？
**要点**：不能，必须 `sum/sum`。
**展开**：直接平均会让大额订单被算术平均稀释，正确做法是 `GMV ÷ 订单量`，先汇总后相除。这也是我们反复强调"先定口径再算数"的原因。

### Q7：怎么保证 ADS 和预测口径一致？
**要点**：共用同一口径源头 + 统一目标变量。
**展开**：建立《指标口径对照表》，ADS、预测、大屏、NL2SQL 全部引用同一定义。预测的目标变量 y 直接取 ADS 的同口径 GMV，从源头杜绝了手册难点 D1"指标对不上"。

### Q8：复购率口径有什么坑？
**要点**：窗口必须注明，180 天与自然月不可混用。
**展开**：复购率 = 下单≥2 次用户数 ÷ 下单用户数。180 天累计口径天然高于自然月口径，两者不可混用；对外汇报必须注明窗口，否则会造成误解。

## 三、AI 边界类

### Q9：NL2SQL 如何保证生成的 SQL 安全？
**要点**：SQL 白名单 + 只读账号。
**展开**：大模型生成的 SQL 不直接执行，先经白名单校验，只允许 `select`，禁止 DDL/DML；数据库用只读账号 `bi_readonly`，从机制上杜绝误删改。这是 AI 应用落地的安全底线。

### Q10：没有大模型 API Key 时系统还能用吗？
**要点**：能，自动降级 offline-mock。
**展开**：未配置 Key 时自动进入 offline-mock 模式，用基于 ADS 预计算数据的规则解析替代，链路照常跑通。完整版设 `USE_HIVE=1` 切换实时查询。这体现了系统的鲁棒性。

### Q11：AI 应用的边界在哪里？哪些事它不该做？
**要点**：AI 负责"理解与生成"，不负责"口径定义与最终裁决"。
**展开**：大模型擅长自然语言理解和 SQL 生成，但指标口径必须由人定义并固化在文档中；AI 生成的结果要经白名单校验和只读执行，最终业务判断仍由人负责。AI 是提效工具，不是决策权威——这也是我们项目复盘里强调的边界意识。

### Q8-补：为什么有的材料 GMV 是 905 万、有的是 3970 万？
**要点**：两套数据源——教学替身 vs 真实数仓，最终以真实 Hive 为准。
**展开**：905 万（116192 单）是第3周无 Hive 集群时用 SQLite 模拟生成的数据，用于预测建模与问数链路自检；3970 万（15000 单）是第4周接入真实 Hive 表 `ydsh_dwd.dwd_order` 的结果。二者规模、时间窗、来源都不同，绝不混用。对外汇报和大屏统一用真实 Hive 口径；第3周数字仅在其自身链路内保持口径一致。这正是手册难点"指标对不上"的实战体现——我用《指标口径对照表》明确区分，而不是把两套数字悄悄混在一起。

## 四、部署原理类

### Q12：Docker Compose 如何保证服务启动顺序？
**要点**：`depends_on + healthcheck`。
**展开**：`app` 依赖 `superset`，通过 healthcheck 确保 Superset 健康后才启动 App，避免下游服务连不上上游。一键 `docker compose up -d` 即可拉起全部服务。

### Q13：容器里为什么连不上宿主机的数据库？
**要点**：`localhost` 在容器内指向自身，用网桥网关。
**展开**：容器内的 `localhost` 是容器自己，不是宿主机。`host.docker.internal` 在本环境解析为 IPv6 导致失败，改用 Docker 网桥 IPv4 网关 `172.17.0.1` 解决。这是手册纠错记录 W4-2。

### Q14：密钥是怎么管理的？
**要点**：`.env` 注入 + gitignore，不落盘。
**展开**：所有密钥写在 `.env`，通过 Compose 的 `${VAR}` 注入容器；`.env` 已加入 `.gitignore`，不入 Git、不出现在答辩材料。代码里只提交 `.env.example` 模板。

### Q15：性能做了哪些优化？效果如何？
**要点**：分区裁剪 + 列裁剪 + ADS 预聚合 + 大 key 加盐。
**展开**：ORC 列式存储 + 按月分区，查询带分区条件触发裁剪；ADS 把计算前置离线。真实压测：分区裁剪提速 59%，ADS 预聚合提速 71%。大 key 加盐两阶段聚合缓解数据倾斜。
