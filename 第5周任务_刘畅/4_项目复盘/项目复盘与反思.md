# 项目复盘与反思（Project Retrospective）

> 项目：云购生活新零售——企业级数据仓库与经营分析可视化系统
> 作者：刘畅　日期：2026-11-23
> 依据：手册步骤6——从技术、协作、表达三个维度总结收获与改进计划

---

## 写在前面

五周时间，我把 6 份原始 CSV 做成了一套从数据到决策的完整系统。这不是"做完五个任务"，而是完成了一次从"会做技术"到"能交付项目"的跃迁。以下从技术、协作、表达三个维度复盘。

## 一、技术维度

### 1.1 掌握最扎实的能力

| 能力 | 具体体现 |
|---|---|
| 四层数仓建模 | 独立完成 ODS→DWD→DWS→ADS 分层，星型模型 + 总线矩阵，维度/事实表判定清晰 |
| 数据清洗治理 | 五类脏数据判定规则与处理策略，能解释"缩尾不删除""email 不填充"等取舍理由 |
| 口径管理 | 建立《指标口径对照表》并作为唯一事实源，解决了"指标对不上"的核心难点 |
| 端到端联调 | 逐层行数守恒、GMV 两层一致、7 类问数验证、多端可视化，形成完整验证闭环 |
| 工程化部署 | Docker Compose 一键部署、healthcheck 依赖顺序、密钥不落盘、SQL 白名单 |

### 1.2 仍需加强的方面

| 不足 | 根因 | 改进计划 |
|---|---|---|
| 预测模型较简单 | 数据仅约半年、样本量小，复杂模型易过拟合 | 补充更长历史数据后引入季节性分解（SARIMA）/ 树模型，并做交叉验证 |
| 促销日预测误差大 | 大促日 MAPE 63.2%，促销冲击未在特征中充分刻画 | 增加促销力度、提前期、节假日等特征；对大促单独建模 |
| 两套数据源口径需持续治理 | 教学替身（SQLite）与真实 Hive 数据差异大 | 在项目文档显著位置标注来源，最终交付统一以真实 Hive 为准 |
| Superset 仪表板 UI 操作依赖手工 | 已备好数据层，UI 图表需点选 | 用 Superset API 脚本化创建图表与仪表板，实现完全可复现 |

### 1.3 技术认知的深化

最大的技术收获不是某个工具，而是**"先定口径，再算数"**的工程意识。手册里"指标对不上"被列为首要难点，实战中我体会到：数据一致性的问题几乎都源于口径不统一，而非计算错误。把口径固化为文档、让所有链路引用同一源头，比事后对数高效得多。

## 二、协作维度

### 2.1 收获

- **Git 协同流程**：实践了 Fork / PR / Code Review / Issue 留痕，理解了分支命名（`feature/`、`fix/`）与 Conventional Commits 规范；
- **文档驱动协作**：五大文档统一模板、口径一致，让"各模块可独立开发再整合"成为可能；
- **分工与整合**：五周分阶段推进，每周产出可交付物，最终整合时各模块能对接。

### 2.2 不足与改进

| 不足 | 表现 | 改进计划 |
|---|---|---|
| Git 历史治理滞后 | 远端正停在第2周，第3~5周成果未及时入库；作者身份混用（刘畅/lc242017） | 本周补齐提交并统一身份；后续养成"每周收尾即推送"的习惯 |
| 分支留痕不足 | 实际只用 main 分支，PR 过程未充分体现在分支结构上 | 多人协作时严格按 `feature/模块` 开分支、走 PR 合入 |
| 沟通记录散落 | 协同记录分散在本地文档，未同步到仓库 | 统一纳入 `docs/`，作为 Code Review 书面证据 |

## 三、表达维度

### 3.1 收获

- **文档写作**：完成需求、清洗、架构、部署、API 五大文档，结构统一、可追溯；
- **英文 README**：按国际化规范撰写，可作为开源项目门面；
- **答辩准备**：形成 10 分钟演示脚本 + 5 分钟问答库 + 演练预案的完整答辩材料。

### 3.2 不足与改进

| 不足 | 表现 | 改进计划 |
|---|---|---|
| 演示时间控制 | 内容多，容易在技术细节上超时 | 按脚本分段计时，先讲业务价值再讲技术亮点，可视化段作为弹性缓冲 |
| 突发情况应对 | 现场启动失败风险 | 用截图兜底、预跑结果备用，演练时预演失败场景 |
| 数字表达一致性 | 两套数据源数字不同易被追问 | 统一对外用真实 Hive 口径，并准备好"教学替身 vs 真实数仓"的解释话术 |

## 四、总体结论

五周项目让我完成了一次完整的企业级数据项目交付：从需求定义、数据清洗、数仓建模、预测问数，到可视化部署与答辩准备。技术能力、工程意识、协作规范和表达能力都得到了系统性锻炼。

最重要的三点经验：

1. **口径是数据项目的地基**——先固化口径再算数，能避免绝大多数"对不上"问题；
2. **可复现比跑通一次更重要**——一键部署、脚本可重跑、文档可追溯，才是"能交付项目"的标志；
3. **诚实标注边界**——教学替身与真实数据的差异、模型的误差来源、AI 的能力边界，如实说明比掩盖更专业。

后续我将补强预测模型与 UI 自动化，并把 Git 治理习惯固化下来，持续把这个项目打磨成真正可开源的成果。
