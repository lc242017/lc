# 需求文档（Requirements Specification）

> 项目：云购生活新零售——企业级数据仓库与经营分析可视化系统
> 版本：v1.0（第5周整合定稿）　维护人：刘畅　日期：2026-11-23
> 定位：五大文档之首，定义业务背景、需求范围与指标体系；其余四份文档均以本文为需求源头。

---

## 一、业务背景

云购生活是一家新零售企业，业务覆盖线上商城与线下 60 家门店，经营 8 大品类商品。随着业务规模扩大，存在以下痛点：

1. **数据分散**：订单、用户、商品、行为等数据分散在多个源系统（CSV 导出），缺乏统一口径；
2. **口径不一**：各业务部门对 GMV、客单价、复购率的定义不一致，汇报数据经常"对不上"；
3. **分析滞后**：经营分析依赖人工 Excel 汇总，无法快速响应管理层问数需求；
4. **缺乏预测**：没有销售趋势预测能力，备货与营销决策缺少数据依据。

## 二、项目目标

构建一个从原始数据到经营决策的端到端数据系统，实现五周递进目标：

| 周次 | 阶段目标 | 核心产出 |
|---|---|---|
| 第1周 | 数据采集与质量预评估 | ODS 贴源层 6 张表、质量预评估表 |
| 第2周 | 数据清洗与四层数仓建模 | 五类脏数据清洗、DWD 维度建模、探索性分析 |
| 第3周 | DWS/ADS 汇总与预测问数 | KPI 指标、GMV 预测、NL2SQL 智能问数 |
| 第4周 | 可视化与部署 | Superset 仪表板、ECharts 大屏、Streamlit 问答、Docker 一键部署 |
| 第5周 | 整合冲刺与交付答辩 | 端到端联调、五大文档、英文 README、答辩演练 |

## 四、指标体系定义

> 完整口径见 `第3周任务_刘畅/1_建模与ETL脚本/指标定义文档_metrics.md`（v1.2），此处为需求层摘要。

| 指标 | 计算口径 | 单位 | 优先级 |
|---|---|---|---|
| GMV | `sum(pay_amount) where status='paid'`（实付、剔除退款） | 元 | P0 |
| 订单量 | `count(distinct order_id)` | 单 | P0 |
| 客单价 | `GMV ÷ 订单量`（先汇总后相除） | 元 | P0 |
| 活跃用户数 | `count(distinct user_id) where status='paid'` | 人 | P1 |
| 复购率 | `下单≥2次用户数 ÷ 下单用户数`（注明窗口） | % | P1 |
| 品类销售占比 | `品类GMV ÷ 全部GMV` | % | P2 |

## 五、非功能需求

| 类别 | 要求 |
|---|---|
| 一致性 | 各层行数与指标值逻辑自洽；ADS 与预测、大屏口径统一 |
| 可复现性 | 一键部署；脚本 `drop+overwrite` 可重跑 |
| 安全性 | 密钥经 `.env` 注入并加入 gitignore；NL2SQL 走 SQL 白名单，仅只读账号 |
| 性能 | 分区裁剪、列裁剪、ADS 预聚合；压测相对全表扫描提速 29%~71% |
| 规范性 | 文档结构统一、可追溯；Git 提交遵循 Conventional Commits |

## 六、验收标准

1. 端到端数据链路 ODS→DWD→DWS→ADS→应用逐层核对通过（见 `0_端到端联调/端到端联调核对清单.md`）；
2. 五大文档结构统一、内容完整、可追溯；
3. 英文 README 可作为开源项目门面；
4. Git 主干历史清晰、分支命名规范、无敏感信息泄露；
5. 答辩 PPT + 10 分钟演示 + 5 分钟问答准备就绪。
