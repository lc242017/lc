# AI 应用反思

第 3 周实训 · 云购生活新零售数据仓库项目　|　数据分析组　|　2026-11-13

## 一、我们在哪些环节用了 AI

| 环节 | 用法 | 模式 |
|---|---|---|
| NL2SQL（子任务 4） | 自然语言 → 生成 SQL → 执行 → 返回结果 | OpenAI 兼容协议；未配置 Key 时走离线模板引擎 |
| 智能洞察（子任务 5） | 异常日归因假设、经营摘要初稿 | 同上，离线模板按确定性规则生成 |

两种模式共用同一套代码路径（`llm/client.py`），区别只在 `chat()` 的实现分支；
配置 `DEEPSEEK_API_KEY` 后无需改代码即可切换为真实大模型。

## 二、实测中发现的 AI 局限（不是假设，是我们真踩到的）

1. **模板变量注入错误**：LangChain 的 `ChatPromptTemplate` 会把系统提示词里的
   `{"sql": ...}` 当成模板变量，直接抛 `KeyError('"sql"')`。这说明 AI 开发工具链
   的"便利抽象"会静默改变语义，必须实测，不能只看文档。
2. **离线模板不是大模型**：模板引擎只是确定性规则，输出"看起来像 AI"但没有推理。
   我们在报告头显式标注"非真实 LLM 输出"，避免评审误判。把模板输出当成智能，
   是本周最容易自欺的地方。
3. **幻觉风险必须用机制约束而不是口头提醒**：我们要求大模型"只依据给定数据"，
   但真正的防线是 `verify_ai_text()`——从 AI 文本抽取全部金额/百分比，逐一回查
   ADS 表。离线模板 60/60 全部可溯源；接入真实大模型后，WARN 项（未命中数据池
   的数字）会被强制列出，需人工复核才能进入决策材料。
4. **归因≠因果**：异常日归因只用了"促销日历 + 前一交易日 z 值 + 星期画像"三类
   数据内证据。GMV 突降可能与库存断货、竞对动作、舆情相关，这些都不在数据里——
   报告对此类日期一律输出"需人工排查"，不假装能解释。

## 三、偏见与风险的批判性分析

- **数据边界即模型边界**：180 天窗口做不了同比；模拟数据的"周内效应/会员日脉冲"
  强度由生成参数决定，真实业务未必如此分布。AI 对输入分布的偏差没有免疫力。
- **Prompt 设计自带立场**：系统提示词约束了表名/口径/只读，这既是安全护栏，
  也把分析视角限定在我们预先想到的问题上——AI 不会主动问"你们有没有考虑过
  另一种口径"。
- **自动化报告的"流畅性错觉"**：文字通顺 ≠ 结论正确。评审者（包括我们自己）
  容易被结构完整、语气专业的输出说服，因此我们把"数字验证明细"作为报告的
  固定章节，让验证成本可见。

## 四、我们采用的审慎验证流程

```
异常检测(统计规则) → 组装数据上下文 → 大模型生成归因/摘要
        → 数字抽取回查（PASS/WARN）→ WARN 人工复核 → 才可引用
```

- SQL 侧：`SQLGuard` 白名单 + 连接级 `query_only`，AI 生成的 SQL 写不进任何表；
- 洞察侧：数字回查 + 事件日历交叉验证 + 强制"需人工验证"标注；
- 流程侧：AI 产物全部 git 留痕（`output/ai_insight_report.md`、`ai_insight.json`），
  可追溯、可复算。

## 五、结论

AI 在本周的价值是"把已经算清楚的数字组织成经营语言"，而不是替我们想清楚问题。
它的可靠程度完全取决于我们给它的数据口径、验证机制和边界约束。下一阶段若接入
真实大模型，优先要做的不是调 Prompt，而是把 WARN 阈值、事件日历和库存/营销费用
数据源补齐——让 AI 说话之前，先让它有据可查。
