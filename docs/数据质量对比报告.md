## 〇、口径声明（先读这段，否则下面的数字会被误读）

1. **「清洗前」「清洗后」「修复率」全部由 `04_quality_report.sql` 一次算出并落表**，不是先有结论再填数。复算命令见附录 A，任何一条都能当场重跑核对。
2. **枚举类用「值域校验」判定，不是「清洗前后自比」**：不清洗的字段直接判"取值是否在规范值域内"，这样 after 有独立判据，不会出现 `case when` 的 `else` 兜底导致"永远 100%"的假结论。
3. **修复率的分母是「清洗前脏数据行数」**，不是总行数。`before = 0` 时输出 NULL——本来就没有脏数据，谈不上"修复率 100%"。
4. **计数单位不同，不可相加跨越**：「枚举不规范」是**行级**计数（一行只要任一字段脏就算 1 行），「重复值」是**冗余行数**。两者口径不同，第五节汇总只做同类内的纵向对比。

## 五、处理策略与理由（答辩重点）

### 5.1 为什么异常金额用「缩尾」而不是「删除」

第 1 周的教训是"异常值误删"会把正常大额订单一起干掉。假设某笔 30 万元的企业采购订单被判定为异常删除，GMV 立刻少 30 万，而这个错误在报表上完全看不出来——只是数字小了一点。

**缩尾（winsorize）的做法**：把超过 IQR 稳健上界的值替换为该上界（初版曾用 P99，因 P99 被异常值污染而废弃），行保留、订单数不变，只把极端值拉回合理区间。代价是该订单金额失真，但这个失真**可量化、可追溯**（`is_amount_fixed = 1` 可精确查出受影响行数），比静默丢行可控得多。

### 5.2 为什么年龄用「有效区间均值」而不是「全表均值」

若直接用 `avg(age)`，样本里 −3 岁和 200 岁会同时把均值拉偏。正确做法是先 `where age between 1 and 120` 过滤出有效样本再取均值（实测 **41.23**），然后用这个值回填。

同样的道理，**不能用"看起来更稳"的统计量随意替换**——年龄分布右偏是已知特性，保持与其他报表口径一致比追求"更准"更重要。

### 5.3 为什么 `email` 缺失不填充

193 条缺失（19.3%）的邮箱**无法从任何其他字段推断**。用 "user_id@example.com" 之类的方式填充，本质是伪造数据：后续做邮件触达会全部投递失败，而且没人知道这些是假地址。

正确做法是保留 NULL + 加标记位 `is_email_missing`，让下游自己决定：做用户画像时排除这 193 人，做覆盖率统计时把他们算作分母。

### 5.4 为什么去重保留"时间最晚 + 金额最大"那条

订单重复通常是同一笔订单被重复推送。取"时间最晚"是因为后到的记录一般包含状态更新（如从"待支付"变"已支付"），信息更新；同时间再取"金额最大"是为了在完全重复时有个确定性规则，保证**每次重跑结果一致**（否则 `row_number()` 在并列时结果不稳定，跑两次数字不同，无法复现）。

### 5.5 为什么日期认不出时置 NULL 而不猜

`register_date` 若出现 `2025.13.45` 这种明显非法的值，任何"修正"都是猜测。置 NULL 会让它在"注册日期为空"的统计里显形，逼着业务回头查源系统；而随手填成当月 1 号，则会永久掩盖这个数据源问题。

## 六、执行过程中发现并修复的问题

这一节是本周最真实的部分：以下 5 个问题都是**脚本写完后实跑才暴露**的，全部已修复并重跑验证。

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | `Invalid column reference 'price'` | 源表 `ods_order_item` 字段名是 `unit_price`，脚本按 `price` 写 | 02/04 改为 `unit_price`，视图内别名为 `price` 与 DWD DDL 对齐 |
| 2 | 行为时间 6,088 行解析为 NULL | `behavior_time` 存在两种真实格式：`yyyy-MM-dd HH:mm:ss`（53,912 行）与 `yyyy/MM/dd HH:mm`（6,088 行，斜杠且缺秒） | 02 增加格式探测：长度 16 时换斜杠并补 `:00`，归一后残留 0 |
| 3 | 优惠金额清洗后残留 **280** 行 | 截断条件用的是**原始** `pay_amount`；当支付金额为负（已归零）时 `discount > pay_amount` 成立，优惠反被截断成负数 | `v_order_clean` 拆两层：内层先算干净 `pay_amount`，外层据此截断优惠 |
| 4 | `dim_date` 生成 0 行 | Hive 没有 `sequence()`（那是 Spark 函数），报 `Invalid function sequence` | 改用 `repeat(',',n)` + `split` + `posexplode` 造序列，生成 1,096 天 |
| 5 | `dwd_order` / `dwd_order_item` 加载后 0 行 | 一次性新增 366 个分区，Derby 单事务提交失败（`Exception rolling back to savepoint`），整条 insert 回滚 | 13 脚本按月拆成 12 条 insert，每次约 30 个分区，提交稳定 |
| 6 | **异常金额一条都没拦住**（310 条负值处理了，超上限的 304 条全部漏过） | 约 2% 的订单金额被放大 100~2000 倍，P99 已被污染（568 万），P99×3 阈值比最大值还高 | 改用 IQR 稳健上界 P75+3×IQR = 11,356.33，重新识别 622 行 |

> 另有两个引擎层现象值得记录，避免下周重复踩：
> - **Tez 计数器上限 120**：单条 SQL 的 union 分支超过约 3 个就可能报 `Too many counters: 121 max=120`，事务整体失败。04 报告因此拆成 6 批 `insert`，02 验收拆成 2 条。
> - **`hive.exec.max.dynamic.partitions.pernode` 是容器级累计**，不是单 task 计数，不能按"分区数 < 上限"来设。

## 九、结论

1. **五类脏数据全部处理完毕且可验收**：每一项都有判定规则、处理动作、验收 SQL 和实跑数字，不存在"处理了但没法验证"的环节。
2. **清洗不牺牲数据量**：订单 15,600 → 15,000（仅去重减 600），异常金额用缩尾而非删除，GMV 不因清洗产生系统性偏差。
3. **总修复率 99.71%**，未修复的 0.29% 是 193 条 email，属刻意保留。
4. **修复率不是越高越好**：email 0% 是正确结果；反之若枚举类出现「其他」计数，即便显示 100% 也要回头查漏。
5. **手册的"约 900"与实际差两个数量级**，报告统一采用实测口径，并在第七节列出全部差异。
